## Why it matters

ECC is a repository and distribution system for coding-agent workflows: prompt-based agents, reusable skills, rules, hooks, installer/CLI code, MCP configuration and memory features. The publisher describes it as an agent harness optimization system. The repository is not one agent, one Codex skill, or one MCP server. Its suggested uses are software engineering planning, testing, review, documentation and security workflow assistance across general industries; effectiveness and professional suitability were not tested. The canonical `affaan-m/ECC` URL occurs once in the 49-record FavRepos catalog. [R1][R3]

## Architecture and behavior

ECC's root `AGENTS.md` routes tasks to named agent definitions and proposes planning, TDD, review and security procedures. These are instructions to an agent, not proof that every harness loads all 71 agent definitions or enforces the procedures. The `skills/` directory is the canonical workflow source; the Codex plugin manifest points there, while the navigation guide describes `.agents/skills/` as another Codex-facing surface. Legacy commands are entry shims. Selective rules can be loaded as persistent standards. [R3][R4][R7]

Hooks are executable commands triggered by host events. The Codex native projection at the reviewed commit has only `SessionStart`, implemented as a Node bootstrap that resolves the plugin root and invokes a session-start script. The broader Claude hook configuration includes tool interception and observation, so Claude claims about blocking, memory capture or automatic learning must not be attributed to the Codex plugin. Codex hook trust is a separate user decision according to upstream documentation. [R5][R12]

ECC describes two distinct memory mechanisms: session summaries/instincts associated with hook observation, and an optional portable Markdown Memory Vault with project, team and user scopes. The latter requires a separate `ecc-universal` runtime for CLI or optional MCP use. Stored memories are unreviewed content; recall should not be treated as governing policy. Cross-project or cross-harness leakage depends on chosen paths and scopes. No retention, privacy or isolation guarantee was tested. [R1][R8]

## Requirements and integration

The documented universal installer requires Node.js 18+. Claude plugin setup additionally requires Git and Claude Code 2.1+ on `PATH`; those are **Claude setup** prerequisites, not generic Codex prerequisites. The native Codex path requires a Codex build with plugin marketplace support, a plugin installation in the active `CODEX_HOME`, and separate review/trust of its hook. The repository's Codex notes name Codex 0.146.0+ for `plugin add`; this is an upstream compatibility statement, not a version tested here. Native `SessionStart` and the default MCP command require Node; the MCP command also requires `npx` and may fetch its pinned package on first use. No GPU or ECC-hosted account is established as necessary for core local workflows. Optional skills, model providers, browser debugging, GitHub App/Pro, and AgentShield have separate requirements or possible charges. Exact API/model cost depends on the chosen harness and usage. [R1][R4][R5][R6][R12]

The native Codex plugin path and legacy sync are separate. The legacy script edits `~/.codex` configuration and an `AGENTS.md` block, copies support files, generates prompts, merges MCP settings and records ownership for later cleanup. The reviewed script also reads global Git hook configuration. These are material configuration changes; a dry-run and backup review would be necessary before any future adoption. Installing both native plugin and legacy sync can duplicate surfaces. Claude plugin plus a full manual Claude install has a similar conflict. The project-local `.codex/config.toml` enables multi-agent roles, but those roles are distinct from the repository's Claude-style `agents/` collection and may interact with a user's existing instructions or policies. None of these paths was executed. [R1][R7][R12][R13]

The upstream platform matrix lists Linux/macOS as core-supported, Windows/WSL as core-supported and native Windows with limitations. Some optional paths need Bash or Python. Reported Windows defects affect continuous learning and memory writes. This is documented support status, not validation on any OS. [R1]

## Token and context impact

The publisher intends skills to load on demand, while always-loaded rules, agent instructions, tool schemas, recalled memories and session-start context consume prompt space. The plugin advertises a large catalog, and delegation opens additional model contexts. The single default MCP server still adds a tool surface if enabled. ECC's own guidance warns that broad MCP enablement and agent teams increase token use; its Claude-specific model and compaction settings are not evidence of savings in Codex. `ECC_SESSION_START_MAX_CHARS` and related controls are documented, but effective Codex behavior was not measured. No token counts, cost reduction percentages or quality gains are independently established for this review. [R1][R11][R14]

## Security, privacy, and license

The Codex plugin manifest requests interactive, read and write capabilities; the actual permission boundary remains the host's policies and user choices. A trusted `SessionStart` hook executes Node code. The default MCP definition can launch an npm package and browser debugging can expose page data or credentials to that server. Review package provenance, browser access, hook source and changed definitions before enabling them. The repository's security policy provides a private reporting route and support targets, but those are publisher commitments, not evidence that the package or any optional service is safe. [R4][R5][R6][R10][R12]

ECC's optional memory and learning paths can store prompts, tool events, project identifiers or summaries locally. Team memories may be version-controlled; user and project scope must be checked before sharing. AgentShield is a separate `ecc-agentshield` package and its automated findings are not a substitute for an independent audit. The README's test-count, coverage and scanner-rule figures are developer claims. No data flow to the ECC Pro GitHub App was evaluated, so its permissions, retention and pricing require a separate assessment before connection. [R1][R8][R10]

The repository LICENSE is MIT, with notice retention. That covers the repository's licensed material; third-party npm/MCP packages, models, APIs and connected services have separate terms. The presence of an MIT file does not establish that every dependency or external asset is under MIT. [R9]

## Maintenance, alternatives and open questions

GitHub listed `v2.2.3` as its latest published release at review time, while inspected main was a later commit. This establishes recent activity, not future maintenance or release reliability. The repository's own support matrix calls Claude Code its primary harness and Codex partial. A smaller set of manually reviewed Codex skills, native Codex instructions/roles, or task-specific MCP servers are **possible alternatives**, not products evaluated here. [R1][R2]

Open questions for an authorized, isolated pilot: Which skills are actually discovered by the intended Codex build? What exactly does the trusted SessionStart hook read, write and inject? Is the default MCP enabled automatically, and with what browser access? How do existing instructions, skills and MCP names collide? What are prompt and billing-token deltas against a controlled baseline? How do uninstall and update preserve user configuration? Which optional memory features work in Codex and native Windows? None has a tested answer in this draft.
