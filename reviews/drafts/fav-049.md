## Why it matters

Cloudflare Security Audit is one agent skill for guiding source-first security reviews of a codebase. It organizes reconnaissance, coverage-led hunting, adversarial validation, structured findings, a further record-verification step, and target-neutral reports. Its value proposition is a repeatable, evidence-oriented workflow for coding agents; the repository does not provide a standalone vulnerability scanner or certify the target as secure. The README says this skill was the single-repository starting point for a larger Cloudflare vulnerability-discovery harness. That is an upstream statement, not an independently validated performance result. [S1, S2]

The scope is generic software development and application security. The material contains attack-class guidance for several areas, including application access control, web and authentication protocols, AI/LLM systems, cloud deployment, supply chain, native code, and data isolation. The presence of these guides does not establish complete coverage of OWASP, CWE, CVE, or any other taxonomy. [S2, S4, S5]

## Architecture and workflow

The repository contains a single skill named `security-audit`. Its front matter provides the skill name and trigger description. `SKILL.md` is the setup and orchestration entrypoint; the companion material supplies reconnaissance prompts, hunting instructions and attack classes, domain-specific guides, validation/reporting instructions, a JSON Schema, two zero-dependency Node.js validators, and their tests. The executable JavaScript files are validators for output artifacts, not scanners of the target code. The project relies on a coding agent with tool use and parallel sub-agent/task support for the actual source analysis. [S1, S2]

The documented audit process is:

1. **Reconnaissance and inventory:** map architecture, trust boundaries, input surfaces, source-visible deployment paths, prior evidence, and deterministic coverage units. Four research roles examine product/stack, authority/controls, input-to-sink paths, and local execution/deployment visibility. Reconnaissance is instructed not to execute or send inputs. [S2, S4]
2. **Coverage-led hunting:** assign ledger units to isolated hunters; rank work by trust level, protected assets, prior gaps, and source-grounded priorities; record coverage and gaps. [S2, S5]
3. **Candidate validation:** a fresh verifier who did not find a candidate attempts to disprove it, re-reads cited source, checks controls and conditions, and independently performs a decisive check only when it can be reproduced safely. [S3]
4. **Structured output:** produce `findings.json` with `confirmed`, `needs_validation`, and `rejected` branches, then validate it against `report-schema.json` and validate the coverage ledger. [S1, S3, S6, S7]
5. **Independent record verification:** fresh agents verify final structured source claims and reconcile changes; material replacements receive additional verification. This is independence within a single agent workflow, not third-party external assurance. [S1, S3]
6. **Reporting:** derive `REPORT.md`, `FINDINGS-DETAIL.md`, and `NEEDS-VALIDATION.md` from the findings and coverage ledger. [S1, S3]

The docs specify source inspection and optionally bounded local tests as different evidence methods. For a finding to be `confirmed`, the instructions require a source trace plus an observed, bounded result with concrete impact across a stated boundary. A source-grounded hypothesis blocked by a decisive unknown is `needs_validation`, without severity. A refuted candidate is `rejected`. This review inspected documents and source text only. It did not run target code, a scanner, tests, fuzzers, validators, or any live check, and it reports no vulnerability in any target. [S2, S3, S5]

The guidance identifies false-positive controls: fresh adversarial verification, source-trace reconstruction, boundary/impact requirements, checks for preventing controls, and explicit rejection when evidence refutes a candidate. Falsely negative results remain possible: the README says runs are additive and claims that one run found roughly half of the vulnerabilities that repeated runs found in the project's own test runs. That figure is an author-reported claim with no dataset or independent replication established in this review. [S1, S3]

The inspected materials do not establish full coverage of any named industry taxonomy. Attack-class guides are a project-maintained, extensible checklist, and the workflow itself says that a single pass is incomplete. Coverage depends on target scope, source visibility, run profile/budget, agent/model capability, tools, and the completeness of the coverage ledger. [S2, S4, S5]

## Finding verification

“Independently verified” refers to new agents or stages in the same run performing work distinct from the original hunter. The candidate verifier must attempt to refute the claim, reconstruct the source path and controls, and reproduce a decisive local result when possible. A further fresh-agent stage reviews final structured records. These are meaningful workflow instructions, but they are not an independent external security audit, independent third-party certification, or mandatory human review. The docs do not require a human sign-off before a record is labeled `confirmed`. [S1, S2, S3]

Reproduction is required by the documented `confirmed` evidence contract, but the verifier can only reproduce what is safely and locally testable. When a necessary deployment/runtime fact is outside available source and local observation, the result must remain `needs_validation` with an explicit blocker and validation plan. A completed JSON record and schema pass do not alone prove that the underlying vulnerability is real: the validator checks format and selected consistency properties, while factual correctness depends on the agents' source analysis and bounded evidence. No finding from the skill was evaluated in this FavRepos review. [S2, S3, S6, S7]

## Machine-readable output

The primary machine-readable artifacts are `coverage-ledger.json` and `findings.json`. Findings use a stable fingerprint, title/description, verdict, source trace, evidence with repository-relative file and positive line number, and fields specific to the verdict. Confirmed records include conditions, target-neutral execution/reproduction details and observed result, remediation strategy, likelihood, impact, overall severity, and confidence. `needs_validation` records include blockers and a local and/or deployment validation plan, but no severity. `rejected` records include a reason. The schema disallows unrecognized fields in its verdict branches. The finding validator also checks duplicate/sorted fingerprints and source-path/line invariants. [S3, S6, S7]

No CWE or CVE field was found in the inspected findings schema; no SARIF output or SARIF conformance is documented. The README names JSON schema validation, not CI integration or an export for a security platform. The bundled tests are described as validator and producer-compatible fixture tests; they were not run, so neither schema validation behavior nor test outcomes are asserted here. [S1, S6, S7]

## Sandbox and permissions

The workflow recommends code execution only in an OS-enforced sandbox that disables external networking, starts from an explicit safe environment allowlist, mounts the target and toolchain read-only, restricts writes to agent-specific scratch directories, and applies CPU, memory, process, file-size, disk, and wall-clock limits. It prohibits execution if any control is unavailable. It also provides a detailed parent-side artifact-promotion procedure intended to reject symlinks and special files and enforce path confinement and byte limits. These safeguards are documented design requirements; this review did not verify their operation in any particular agent host. [S2, S3, S5]

When invoked for a real audit, the agent reads a potentially private target repository. The instructions explicitly aim to prevent target-controlled code from receiving host credentials, home directories, sockets, shared services, or retained artifacts, and advise dummy identities/secrets. The actual authority available to the agent and the fidelity of its OS sandbox depend on the host configuration. The package does not establish that sandboxing removes every risk. [S2, S4, S5]

The reviewed files also acknowledge prompt-injection and tool/output risks as attack classes for LLM-backed targets. Untrusted repository content can influence an agent unless the host and operator preserve instruction/data boundaries; the skill is guidance and cannot guarantee model behavior. Findings or reports can expose source paths, sensitive implementation details, reproduction steps, secrets, or internal system information. Review and redact outputs before sharing or publishing them. [S2, S5]

Automated analysis remains dependent on the model's context window and reasoning, selected files and attack classes, ledger quality, tools available, and explicit scope/budget. It can miss code or dependencies and may produce false positives or false negatives. Static review does not prove runtime behavior; local checks may not match deployment; and tests of one path do not establish system-wide security. Reproduction can be difficult when dependencies, identities, services, or deployment controls are unavailable. A clean report, validator pass, or lack of findings is not a guarantee that the target is secure after review. [S2, S3, S4, S5, S6]
