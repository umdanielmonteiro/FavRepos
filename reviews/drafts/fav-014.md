## Why it matters

ComfyUI is a locally runnable visual application and Python backend for constructing and executing generative-media workflows as directed graphs of connected nodes. The upstream describes image, video, 3D, audio and text workflows, reusable subgraphs/templates, App Mode, a local API, asynchronous queueing, partial graph re-execution, model offloading and quantized model support. These capabilities make it a possible component in creative production, prototyping and media pipeline automation; those sector uses are inferences, not measured product-market fit. [R1][R2]

The graph editor, core nodes, local backend and documented HTTP API belong to ComfyUI Core. Community custom nodes are third-party Python extensions and can add functions or dependencies. Model weights are separate downloaded assets with their own publishers and terms. Partner/API nodes and Comfy Cloud are additional offerings that may depend on remote services, accounts or payment; they are not proof that every workflow is offline or included in the core license. The README says core stays offline unless external features are requested and documents a flag to disable API nodes. [R1][R2]

## Architecture and implementation notes

The interface represents node inputs, outputs, parameters and links as a graph. The backend queues prompt graphs and schedules node execution; the HTTP API describes queue, history, object/node metadata and related workflow routes. The implementation registers custom-node routes and frontend extensions, so installing such packages can change both server and user-interface behavior. [R2][R3][R4]

A saved workflow describes an execution plan but may depend on node packages, model files, custom code, templates, and external endpoints that are not embedded in the JSON. A workflow can therefore fail, download artifacts, make external calls or execute code via installed extension nodes depending on its dependencies and configuration. This operational risk follows from the documented architecture and custom-node execution model; no malicious workflow was executed. [R2][R4][R6]

## Requirements and integration

**Runtime and hardware.** The repository documents Python 3.13 as well supported and Python 3.12 as a fallback for dependency issues; its current README also discusses Python 3.14. PyTorch is required. NVIDIA guidance depends on GPU generation and matching CUDA/PyTorch builds; AMD support is documented through ROCm, Intel GPUs through XPU, Apple Silicon through PyTorch for Mac, with other accelerator-specific instructions including Ascend. CPU operation is possible in some packaged/platform paths but will have model- and workload-dependent performance. There is no single supported minimum GPU, CUDA version or VRAM figure applicable to all models and graphs, so benchmark-style requirements remain unknown here. [R1]

**Workflow/API.** A local server exposes an HTTP API, including prompt submission and WebSocket/event capabilities. Applications can call it, but they need an installed, running instance and must address authentication, network exposure, job limits and file access in their own deployment. [R2][R3]

**Codex.** No first-party Codex-specific compatibility claim was found for ComfyUI Core in the inspected sources. Codex may interact with an already available HTTP API or a separate MCP adapter, subject to host permissions and user confirmation; this is generic interoperability, not native Codex support. Custom nodes or workflows do not become Codex skills merely because an agent can inspect their files. [R1][R3]

**Costs.** The core repository is available under GPL-3.0. Compute, electricity, storage, model downloads, GPU/cloud hosting, third-party custom nodes, partner APIs and Comfy Cloud may add costs. The README identifies certain API nodes as optional paid services; actual prices and terms depend on the selected service and were not audited. [R1]

## Security, privacy, and license

The previously viewed branch-relative security policy assumes a localhost-only server, trusted access by anyone who can reach its URL, recent dependencies, and no untrusted custom nodes; the candidate copy was not confirmed. It explicitly describes custom nodes as arbitrary Python code. Exposing the server with a listen-address option or reverse proxy changes that threat model and requires separate network access controls. Workflows may contain prompt text, filenames, metadata and references to private inputs; custom nodes can access files and network according to the process's operating-system permissions. [R6]

The previously viewed branch-relative `LICENSE` identifies GPL-3.0 for ComfyUI Core, but that file could not be confirmed at the candidate SHA. This license does not grant rights to separately published model weights, custom-node packages, workflow templates, partner services or generated/source media. Confirm each component's license, acceptable-use terms and provenance. Model download and extension installation also introduce supply-chain and unsafe-file risks. ComfyUI's security policy is a maintainer-scoped reporting policy, not an independent security certification. [R5][R6]

## Limitations and maintenance

The core, frontend, workflow templates, desktop/portable distributions, custom nodes and model ecosystem have separate release and compatibility cycles. The README cautions that commits outside stable release tags may be unstable and can break custom nodes. Exact VRAM needs, extension compatibility, performance, output quality, third-party licenses and the behavior of any selected cloud/API provider require case-specific review. The current README's superlative performance wording is a maintainer claim and was not independently validated. [R1]
