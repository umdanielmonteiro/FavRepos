## Why it matters

This resource is the `trycompai/crm` repository, distinct from the organization's separate `trycompai/comp` compliance product. It is an agent-oriented CRM application whose scheduled research agent reads and enriches CRM context, proposes or records evidence-backed facts, and schedules follow-ups. Sales and B2B relationship operations are plausible contexts by inference; fit for a particular company is not proven.

The documented stack is Bun/Turborepo, Next.js, NestJS with tRPC, Prisma/PostgreSQL, Better Auth, Vercel's `eve` durable-agent framework and model gateway, plus Vercel Sandbox in production or Docker/microsandbox locally. A CRM can store contacts, companies, deals, notes/history and enrichment facts, but the project documentation emphasizes agent research workflows rather than a conventional generalized CRM feature set.

## Requirements and integration

The quick start requires Bun and Docker/PostgreSQL. Deployment separates app, API, and agent and requires agreement on database/auth secrets. Google or Microsoft identity provider setup is documented; optional external services include Perplexity web search, Context/LinkedIn data, Vercel Blob, and Redis. Mailbox synchronization requires OAuth permissions and a configured scheduler. Hosted Vercel services may incur charges; local Docker avoids some hosted runtime dependencies but does not remove provider/API costs. Exact current service prices were not assessed.

Agent tools can read CRM history, search CRM data, identify contacts, research people, enrich companies, record facts, and schedule rechecks. The docs describe an isolated sandbox with no database and deny-all egress, while some lookups run in the application/provider runtime. This is a documented design, not a verified security boundary.

No Codex-specific skill, plugin, MCP server, or Codex integration was found in the reviewed release docs. Generic ability to access HTTP/tRPC APIs is not native Codex compatibility.

## Security, privacy, and license

The release security policy explicitly states that sign-in is the entire authorization model: all signed-in users can read and write every record; there are no roles, per-record permissions, or organizations. A broad consumer email domain in `ALLOWED_SIGN_IN` can make access open to that domain, while an unset allow-list fails closed. Deployment operators can access database, environment, and logs. Customer email, contact information, identity, and enrichment results should therefore be treated as sensitive. OAuth scopes, third-party data sources, API keys, sandbox behavior, retention, backups, and deletion require deployment-specific review.

The application code is MIT-licensed. Dependencies, Vercel `eve`/sandbox/gateway terms, and third-party data services have separate conditions. The hosted product/service terms were not reviewed.
