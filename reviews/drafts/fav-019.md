## Why it matters

OpenClaw is a self-hosted assistant gateway that connects messaging channels and user interfaces to AI agents and their tools. The project targets developers, power users and teams wishing to interact with an always-available assistant through chat applications. The maintainers describe it as running on user hardware with no hosted service in the middle; that is a project claim, not a verified end-to-end data-flow property. The repository identity and owner match the catalog entry. [R1]

Potential professional activities include developer assistance, internal knowledge workflows and message-driven task automation. Possible sectors are software development, education, research and professional services, subject to access-control, privacy and operational review. These are inferred uses, not validated deployments.

## Architecture and capabilities

The documented topology has chat apps and plugins entering a single Gateway, which is the source of truth for sessions, routing and channel connections. The Gateway exposes or coordinates the OpenClaw agent, CLI, browser control UI, macOS app and iOS/Android nodes. The documentation lists sessions, memory, multi-agent routing, scheduled jobs, hooks, webhooks, browser/dashboard features, and exchange of images, audio and documents. These are documented product capabilities; this report did not inspect the corresponding implementation at a pinned SHA. [R1]

There are three extension categories to keep separate: built-in core tools, official channel/provider/tool plugins that are installed on demand, and skills or third-party plugins created by others. The plugin marketplace's existence does not establish that every extension is trusted, reviewed, sandboxed or covered by the core license. Inspect each extension and its permissions independently. [R1][R3]

## Requirements and integration

**Runtime and operating systems.** The current documentation recommends Node.js 26 and lists Node 24.16+ or 26.1+. It also refers to native Windows Hub, PowerShell and WSL2 Gateway paths, as well as macOS, mobile nodes, containers and server hosting. These are documentation claims, not successful compatibility tests in this review. [R1][R2]

**Installation and persistence.** The documented onboarding starts a foreground Gateway; a CLI command can install a background Gateway service. Configuration resides under the user's OpenClaw directory and controls channels, sessions, providers, access policy and tools. This creates a persistent service and local state whose permissions, update process, backups and secret handling must be managed by the operator. Installation commands were not executed. [R2]

**Models, credentials and costs.** The project supports configuring provider/model choices and local model services. The getting-started guide requires a usable provider route or API key and notes that onboarding may reuse a Codex CLI login. Model inference cost depends on the selected provider, model and account; local inference trades API charges for host hardware, power and storage. This review cannot estimate usage cost. [R1][R2]

**Codex.** The docs explicitly mention detection/reuse of an existing Codex CLI login as an authentication route for OpenClaw. That establishes a documented credential integration with the Codex CLI environment. It does not establish that OpenClaw is itself a Codex plugin, skill, MCP server, or supported Codex extension. Running a command-line tool from another agent would be a separate orchestration possibility, not native integration.

## Security, privacy, and license

OpenClaw is a high-authority agent environment when configured with shell, filesystem, browser, messaging, device or service tools. The project security docs state that untrusted content can arrive through messages, search/fetch results, browser pages, emails, documents and attachments; prompt injection may manipulate the agent. Their mitigations include channel allowlists and pairing, tool policies, execution approvals, sandboxing, limiting agent-to-agent permissions and keeping secrets out of prompts. The security policy frames the intended model as local-first infrastructure operated by a trusted operator, not a multi-tenant boundary among adversarial users sharing one Gateway. These are maintainer guidance and assumptions; they are not a security certification or independent audit. [R3][R4][R5]

The Gateway can run persistently and may store configuration, credentials, sessions, logs and transcripts. Exposing the control plane remotely or granting wide tool access can materially increase impact if an account, plugin, model context or host is compromised. The exact data retained, secrets storage mechanism and isolation behavior can vary by configuration/version and remain unverified here. Review deployment and provider retention terms before using sensitive data. [R3][R5]

The core project is described as MIT licensed. That does not automatically apply to third-party skills, plugins, models, provider services, messaging clients, media or trademarks. Review their licenses and service terms separately. [R1]

## Limitations and maintenance

The documentation itself warns that prompt injection is not solved and that model choice is only one mitigation layer. Tool permissions, approvals, network binding, authentication, sandbox configuration and channel trust remain operator responsibilities. A system that can execute commands or access external services should be evaluated against the precise deployment threat model. No performance or uptime claims were independently assessed.
